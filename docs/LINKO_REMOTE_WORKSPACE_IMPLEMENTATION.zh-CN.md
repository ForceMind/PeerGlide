## 1. 这次具体做了什么

`labs/remote-workspace` 是零第三方依赖、禁止 unsafe 的独立 Rust package，拥有独立 lockfile 和三平台 CI。它不是新建产品：隔离的目的在于先验证纯逻辑，不与现有 GUI/输入/协议主线产生半接通状态。未来进入正式 crates 需专门接线 PR。

| 文件 | 当前代码能力 | 不代表什么 |
| --- | --- | --- |
| geometry.rs | 画布平移、缩放、等比显示、黑边命中拒绝、四向旋转、像素/逻辑坐标、负显示器原点 | 不枚举/调整 OS 显示器，不创建虚拟屏幕 |
| session.rs | 分离观看/控制授权；设备、查看端、连接、对象代次和观看授权代次绑定；过期/撤销/断连；实际展示确认；静态画面来源确认挑战 | 不认证网络，不查询 OS 权限，不发放生产访问凭据 |
| routing.rs | 单目标输入预检、防重放、当前映射核验、切换前释放屏障、空闲失效检查 | 不注入输入，不替代原 runtime，不提供群控 |
| scheduling.rs | 同源多视图复用、可见性/聚焦优先、数量/像素缓存/像素率/目标码率预算、降级和暂停 | 不是实测 GPU/码率保证，不承诺任意并发数量 |
| media.rs | 有界 RGBA 实验帧；先校验固定头部再分配；单帧缓存、版本/代次/序号检查、撤权与过期丢弃 | 没有视频编码器、加密、网络连接或生产媒体协议 |
| handoff.rs | 准备→隐藏请求→远端显示→恢复请求→本地的事务模型；上下文变化取消；真实确认前不宣称恢复成功 | 没有移动/隐藏/恢复系统窗口，没有自动边缘拖窗 |
| workspace_simulation.rs | 双来源模块串联：帧往返、授权、切换、调度、断连及恢复的可执行断言 | 使用 fixture，不能当作真实双机演示 |

观看授权 `view_epoch` 与输入策略 `policy_epoch` 分开：开启控制不打断已合法授权的画面；撤销并重新观看必须拒绝旧授权缓冲区的帧，即便设备和窗口尺寸完全相同。重新连接必须创建新的已认证连接代次，不能把旧 gate 重置为 connected。

## 2. 产品与架构边界

产品使用三种体验，但共享可信设备与会话基础：

1. **桌边协同**：原有 KVM，设备各有桌面，不默认传画面。
2. **远程访问**：选择整个显示器或某个窗口，明确授予观看/控制，可在另一台电脑或未来移动客户端操作。
3. **统一工作空间**：多个已授权 Surface 在一个可平移、缩放的 View 集合中呈现。空间移动不改变来源 OS 拓扑。

“无限”指交互上的平移/缩放，不是无限视频分辨率或无限并发。实验几何坐标限制 ±10^9，缩放 0.05–20；调度最多接收 256 个视图需求、预算最多 64 个解码槽位。这些是输入安全边界，不是可同时运行 64 路视频的性能承诺。默认预算 8 槽位只是实验参数，生产上限由测量决定。

应用始终在来源设备运行。显示代理不迁移进程、账号、安装状态或未保存文件。关闭代理视图默认仅停止分享；“关闭来源应用”是另一项明确操作，不能复用窗口关闭按钮悄悄结束用户工作。

## 3. 总体数据流与模块分工

```text
来源设备                                                        查看/控制端
可信设备身份 ── 独立授权/能力协商 ── 控制通道 ── 会话状态、撤销、源对象代次
OS 画面源 → 采集 → 硬件编码 → 有界发送队列 → 媒体通道 → 解码 → GPU 呈现
OS 窗口/输入后端 ← 原有输入运行时 ← 独立控制租约 ← 输入路由 ← 被选中的 View
                                                      工作空间：布局/缩放/可见性
```

建议边界：

| 模块 | 职责与持有资源 |
| --- | --- |
| DeviceDirectory | 已认证设备与证书指纹、能力、连接引用；发现结果本身不可信 |
| SurfaceRegistry | 来源 OS 对象、临时 ID/代次、几何版本、捕获资格；OS 句柄只留来源本机 |
| SessionCoordinator | 来源/查看端配对、独立授予与撤销、状态机、租约、重连代次、watchdog |
| CaptureAdapter | 用户指定源、系统权限检查、回调/线程所有权、尺寸/关闭/权限变化事件 |
| CodecAdapter | 参数协商、编码/解码会话、关键帧/参数集、设备失败和重建 |
| MediaTransport | 已认证通道、有界分帧/重组、流量/截止时间、拥塞与取消 |
| InputRouter | 精确选择一个获准目标、当前坐标映射、序号与释放屏障 |
| Presenter | 实际展示确认、纹理/缓冲回收、失效画面标识；不通过重画旧纹理假造新帧 |
| Workspace | View 布局、平移、缩放、分组、保存布局；不保存授权票据和截图 |
| NativeWindowBackend | 可选来源窗口尺寸/位置与恢复操作，严格报告提交/完成/未知结果 |

这些是逐步落地的边界，不要求立即造十个空 crate。当前只有表1的纯逻辑；上表中的原生、网络和编解码软件仍需实现。

## 4. Windows/macOS 双向路线

### 4.1 优先：公开 API 的桌面/单窗口分享

macOS：ScreenCaptureKit 作为采集候选；`SCContentFilter(desktopIndependentWindow:)` 可以指定单个窗口，`SCShareableContent` 提供可分享对象。VideoToolbox 是硬件编解码候选；由一个平台 worker 管理采集和编码生命周期。系统授权、源窗口关闭、分辨率变化、黑屏/保护内容和睡眠都必须显式处理。

Windows：Windows.Graphics.Capture 作为采集候选，桌面 Win32 可通过 `IGraphicsCaptureItemInterop::CreateForWindow` 定位选中的窗口；Media Foundation/D3D 是编解码与缓冲共享候选。要处理捕获源关闭、尺寸变化、图形设备丢失、系统隐私与安全桌面。不能因能拿到 HWND 就宣传有窗口级安全控制。

两端分别实现 Source 与 Viewer，因此 Mac→Windows 和 Windows→Mac 共用会话语义，仅平台适配不同。第一版先“用户手动选源→另一端观看→单独同意控制”，保留来源可见；不以虚拟显示驱动作为这个最小闭环的前置依赖。

**窗口采集不等于窗口输入隔离。** 当前实验默认不支持 WindowOnly 控制；来源平台没有可靠目标限定时，只能只读分享，或明确请求整机级控制。焦点/原生对象必须在实际输入提交前重核验。macOS 音频捕获也不能因为选择了单窗口就被描述成严格单窗口音频；音频授权、范围和来源标签单独设计。

### 4.2 可选：虚拟扩展屏模式

虚拟屏解决“OS 自己把窗口拖到额外显示器”的体验，与单窗口代理是两条可并存路线。

- Windows：研究 IddCx / Indirect Display Driver。驱动安装、签名、服务权限、升级和卸载归属需独立评审；不关闭驱动签名验证，不把安装驱动藏在普通连接按钮背后。
- macOS：Osplay 通过私有 `CGVirtualDisplay` 接口实现。将其严格隔离到可选提供者，建立版本能力探测与拒绝/回退；不把它作为核心远控的唯一途径，不承诺 App Store 或未来 macOS 兼容性。
- 保持虚拟屏与窗口资源归属账本。断线只清理本会话拥有的资源；禁止删除其他软件创建的显示器。窗口恢复需要应对来源显示器已拔出，恢复到当前可用屏幕，而非照搬无效坐标。

### 4.3 最后：自然边缘拖窗

先有显式“发送窗口到设备”，再研究原生拖动检测、边缘滞留确认、方向、取消、双向返回和混合 DPI。不能把原有鼠标跨屏触发直接当作窗口跨屏：标题栏、系统吸附、全屏应用、手势、文件拖动各有语义。

隐藏/最小化/移出可见区域后是否仍可持续采集必须逐平台验证。当前 `Handoff` 只验证失败恢复状态机，不证明某种原生隐藏方法可行；未验证前来源保持可见。

## 5. 媒体与传输设计决策

### 当前实验格式

`LWR0` + format version 2 + RGBA codec 标识，固定头 76 字节，大端字段：连接 nonce、对象 ID/代次、几何版本、帧序号、宽高、负载长度、观看授权代次。负载最多 16 MiB，尺寸最多 16384×16384 且必须满足实际 RGBA 大小上限；尺寸上限不绕过字节上限。source/viewer 身份由独立已认证通道绑定，不信任包里的设备名。

这是内存往返参考格式，不注册生产端口或 ALPN，不接入 v5。同步 `Read` 解析器不实现时钟/超时，未来网络适配器必须提供读截止时间、取消、总配额，并在发布和展示前检查当前授权。原始/已解码帧可替换丢弃；编码后的 H.264 参考帧不能套用相同策略。

### 生产媒体支线（待 ADR 和实现）

首个跨平台候选为 H.264、SDR 8-bit；实际硬件能力协商决定 profile、level、最大尺寸、刷新率和软件回退，不能把“有 API”当作硬件编码已可用。零拷贝只是优化方向，需要测量实际内存路径。HDR、HEVC/AV1、4:4:4、音频和游戏手柄分别排期。

复用现有证书身份与信任模型，**不复用 input grant 作为视频许可，不在 v5 input 消息里夹带视频**。建议独立、默认关闭的媒体会话与版本协商；具体采用新 ALPN/连接或经升级协议声明的新通道，须通过 ADR 与双端兼容测试决定。

可先比较有截止时间的逐帧 QUIC stream 与 datagram 重组方案。前者要及时取消过期帧；后者需有界分片数/总长度/会话配额、重组截止时间、有限重传和关键帧恢复。接收端不能根据未经验证的 SPS/负载长度申请任意显存。多路视频应按资源预算公平调度，不能饿死输入、撤销和恢复控制。

断线后不盲目重放输入。新连接重新协商观看授权、控制租约和编解码器状态；旧 nonce/view_epoch/geometry revision/序号一律失效。序号与本地单调时间不能用用户墙钟或远端自报时钟替代。

## 6. 多会话与输入安全

默认一个本地控制器只控制一个目标。多路观看和群控是不同功能；本支线没有输入广播。未来多个查看端竞争一个来源时，来源端必须拥有全局控制租约仲裁，单个客户端的 InputRouter 不能替代该仲裁。

所有输入需要经过“当前会话→当前授权→当前选中视图→当前来源对象/几何→当前输入序号”的重核验。窗口 token/fixture ID/时间戳不构成认证。画布拖动、缩放和窗口调整大小都应使旧映射失效，避免一个旧坐标点击到另一处或另一台电脑。

切换目标前先停止路由，保留旧目标输入释放请求，确认原 runtime 完成对应释放后才允许控制新目标。网络超时不是 OS 已释放的证明；离线接收端的原生 lease/watchdog 仍需独立工作。失败时宁可暂停新控制并提示用户，也不能发假 ACK。选择无权控制的新面板，也必须先让旧面板失去输入目标地位。

双向观看要防止远程视图被再次采集造成递归画面/输入回环。窗口 token 的来源路径只是一层检查，完整桌面包含远程播放器时仍需平台排除/遮蔽能力或拒绝危险组合，不能宣称一个元数据标记已解决系统级递归捕获。

## 7. 静态桌面、卡帧与断线的区别

不能规定“2 秒没收到新画面就一定断网”：静态桌面可能本来没有新采集帧。但也不能用本地不断重画旧纹理、泛用网络心跳，假装当前画面仍然有效。

实验采用两个路径：新 `FrameStamp` 的实际呈现更新状态；静态画面通过查看端发起的短期 `ContentCheck`，来源端在确认采集健康且当前内容仍匹配指定帧后返回。挑战绑定观看授权、对象、几何与已呈现序号，有本地截止时间；一次性消费，重放、过期、新帧到达或重新授权都会使其失效。

**生产适配器尚未实现这个挑战传输与源端内容检查。** 不能为了“让静态画面可操作”自动调用确认方法。没有有效确认时，过期画面停止控制并展示“画面已过期”，保留紧急恢复入口。

## 8. 资源、布局与手机

可见聚焦面板优先质量；背景预览降低刷新/分辨率；屏外暂停。相同 Surface 多个 View 共享解码结果，不因为缩略图存在就重复开解码器。跨不同查看端不能共享授权，但来源可在合法范围复用编码结果；广播给未授权客户端不可接受。

调度预算包含解码槽位、三份 RGBA 输出缓存的参考值、像素率与目标码率。真实生产预算还需驱动/codec参考帧、NV12/纹理、网络发送队列、GPU限额与实际码率反馈。启用一个计划前先确认旧资源已回收或有足够重叠预算，不因算法输出没超限就宣称切换瞬间不会超限。

移动端首要角色是控制电脑，不承诺手机自身可被任意远控。候选 Android：原生 Kotlin UI + MediaCodec；iOS/iPadOS：原生 Swift UI + VideoToolbox/系统呈现组件；Rust 会话核心通过窄 FFI 复用。具体技术栈需最小原型验证，不要求桌面 eframe 直接跨到手机。

手机优先单面板沉浸、概览切换、触屏/触控板模式、虚拟/外接键盘、方向变化、手势与远端输入的区别。IME/文本组合与原有基本 HID 不是同一能力，必须显式协议设计；不记录输入内容。后台、锁屏、蜂窝/Wi-Fi切换必须释放控制或按明确策略降级，不静默恢复敏感控制。

布局保存只含设备引用、View位置/尺寸、分组和偏好，不含授权、nonce、帧缓存、窗口内容、秘密或可重放控制票据。导入文件先限长/版本校验，加载布局不自动开始采集或建立控制。

## 9. 公网支线：没有“打开接口就自动穿透”

现有 QUIC 不自动提供 NAT 穿透、信令、中继或浏览器能力。WAN 是独立支线：已认证 rendezvous、直连优先、失败后端到端加密中继回退，保留撤权与防滥用/连接数/速率/流量配额。中继只搬运密文，不成为屏幕内容解密端；设备认证与中继流量授权是两层问题。

浏览器不能直接运行现有原生输入/QUIC实现。需要浏览器时重新比较 WebRTC、支持环境内的 WebTransport 等适配路线，而不是承诺一套 socket 代码无修改覆盖网页。当前没有上线或部署信令、中继、账号服务，也没有默认无人值守授权。

## 11. 测试与测量要求

自动化应覆盖：头部各字段损坏、所有截断前缀、长度/尺寸溢出、重复/乱序帧、过期授权、旧授权包进入新缓存、断线后重连、失焦/切换释放屏障、重复 ACK、窗口代次重用、静态挑战重放、摄像机/几何变更、同源复用和预算上限。
